### 正文（约 600 字，可直接作为帖子主体）

> **起因**
>
> 学生党吃饭的真实约束不是「这顿多少钱」，而是「这顿吃完，后面几天怎么过」。
> 但常见点餐工具只回答前者。所以我把「单笔消费」放回「周期预算」里重算了一遍。
>
> **它做什么**
>
> 输入一句话：「今天只有 25 元，想吃鸡肉，不要太辣」。
> 系统解析出预算上限、餐次、口味偏好、排除项，然后：
>
> 1. 调 `query-nearby-stores` 拿真实门店（已有门店码时跳过）
> 2. 调 `query-meals` 拿这家店**当前**的菜单与标价
> 3. 做餐品角色分类：酱料、单点饮料、甜品、周边、多人餐全部剔除——它们不算一顿饭
> 4. 构造候选组合，先用标价粗筛
> 5. 对每个候选调 `calculate-price` **逐个核价**，超预算就剔除换下一个（单请求最多核 12 次）
> 6. 四维评分（价格适配 / 组成完整 / 口味偏好 / 性价比）加权，输出三份不同取向的方案
>
> 菜单标价只用于粗筛，**结论只认官方算价**；两者不一致时以算价为准并打标记。
>
> **那个多出来的一步**
>
> `/budget` 页建月度预算后，每记一笔之前会先给一组对比：
> 「吃这顿之前日均 ¥77.54 → 吃之后日均 ¥77.49」。
> 顺带一个我觉得比余额更直观的指标：**消费进度 8% 对比时间进度 71%**——钱花得比时间慢。
>
> **几个刻意的取舍**
>
> - 推荐结果**不会自动进账本**。点「查看推荐」只是只读查询，扣预算必须用户显式确认实付金额。
> - `planned`（计划中）不扣预算，只有 `confirmed`（已消费）才进「已花」。
> - 金额全程用整数「分」，禁止 `parseFloat * 100`——浮点误差会让预算累计算出「多一分钱」。
> - 营养数据**不参与任何判断**。上游的营养接口只有商品名，菜单是 code + name，没有可靠关联键，
>   硬匹配就是编数据。所以 `nutrition` 恒为 `null`，「均衡」只代表价格与组成的折中。
> - `不吃辣` 在**过滤阶段**剔除，不是降分；但上游没有配料表，所以每次都附免责说明，从不宣称「绝对不含」。
>
> **当前状态（如实）**
>
> - 意图解析跑在**规则模式**，未配置大模型密钥；页面有「规则解析（未接入大模型）」徽标。
>   配置后会自动切换，但**真实模型回归还没做**。
> - **没有线上演示站**，需要本地 `npm run dev`。没 token 可以看 `/demo` 的冻结快照。
> - 质量门禁：单元测试 474 项、真实接口集成 26 项、浏览器端到端 69 项断言，当前全部通过。
>
> **代码**
>
> 仓库：`https://github.com/Wen-cmd1/mealmate-ai`（MIT）
> 接口契约与一次真实调用记录：`MCP_INTEGRATION.md`
> 架构决策记录：`docs/decisions.md`
>
> 项目参加了麦当劳程序员创意开发大赛，报名 Issue #1125 已获官方通过。
> 欢迎提 issue 指问题，尤其欢迎指出「这条数据其实不该这么用」这类错误。

## 三、开发者分享版（GitHub 群 / 技术群 / 内部分享）

对应场景：给同行看代码。**重点在结构、边界与可验证性。**

### 短版（约 150 字）

> 分享一个 Next.js 16 + TypeScript 的参赛项目：饭搭子 AI。
> 只读调了麦当劳三个 MCP 工具（查门店 / 查菜单 / 官方算价），做预算内点餐推荐 + 周期预算 + 单笔消费影响预测。
>
> 比较有意思的几点：
> - 金额全程整数分，禁止浮点乘 100
> - 推荐结果绝不自动写入账本，扣预算必须用户确认实付
> - 营养数据因为没有可靠关联键，直接恒为 null，不参与评分
> - 474 单测 + 26 集成 + 69 E2E，集成测试无 token 时整组 skip 而非假装通过
>
> 架构决策都记在 `docs/decisions.md`，50 条左右，写的是「为什么不这么做」。
> https://github.com/Wen-cmd1/mealmate-ai

### 长版（约 400 字，含技术选型）

> **项目**：饭搭子 AI / MealMate AI —— 麦当劳 MCP 参赛作品，MIT 开源。
>
> **技术栈**：Next.js 16.4（App Router）+ React 19 + TypeScript strict + Tailwind 4 + Zod 4 + Vitest 5 + MCP 官方 SDK。
> 无额外运行时依赖，MCP 客户端是手写的薄封装（握手 / 超时 / 信封解析 / 脱敏）。
>
> **三个 MCP 工具，全只读**：`query-nearby-stores`、`query-meals`、`calculate-price`。
> 不碰 create-order / 领券 / 抽奖这些写操作——不是做不到，是刻意不做（下面说原因）。
>
> **三个我认为值得抄走的设计**
>
> 1. **两级价格**：菜单标价只做粗筛，结论必须来自 `calculate-price`。不一致时以算价为准并置 `priceMismatch`。
>    算价抛错就跳过该候选，**绝不回退到标价**——回退等于给用户一个错价。
> 2. **排除 ≠ 降分**：`avoidTags` 走确定性过滤，被排除的餐品连算价请求都不会发起。
>    这既省调用次数，也避免「排除了却还出现在备选里」。
> 3. **模型不能产出数据**：`ParsedIntent` 的类型定义里没有价格、菜品、优惠券字段，
>    模型输出还要过 Zod 白名单，不合法整条丢弃降级。所以「AI 编一个不存在的套餐」在类型层面就不可能。
>
> **为什么不做交易**
> 下单、支付、领券要动用户的真实账户与钱。在没有明确授权、没有对账机制、没有退款路径的前提下，
> 一个学生作品去碰这些是对用户不负责。所以整个项目定位成「只读决策辅助」。
>
> **测试怎么组织的**
> 单测 474 项不联网，用真实抓取的 fixture；集成测试 26 项打真实接口，**无 token 时整组 skip 并标记为未验证**，
> 不把未执行算作通过；浏览器 E2E 69 项断言用 CDP 驱动真实 Chrome。
>
> **已知限制**（README 里列了 16 条，这里挑三条最容易踩的）
> - 限流是进程内滑动窗口，多副本部署会各自计数，生产要换 Redis / 网关
> - 查门店必须「城市 + 商圈关键词」同时给，只给城市上游返回 600058
> - 营养维度完全缺席，任何「热量/营养均衡」的说法都是不成立的
>
> 代码：`https://github.com/Wen-cmd1/mealmate-ai`
> 接口契约：`MCP_INTEGRATION.md`　决策记录：`docs/decisions.md`
