# 架构决策记录（任务 001）

按时间顺序记录本次做过的关键取舍，方便后续任务（002+）不重复踩坑。

---

## ADR-001 采用「项目服务端 MCP SDK 直连」，不依赖 WorkBuddy 会话连接器

**背景**：`~/.workbuddy/mcp.json` 里已配好 mcd-mcp，但当前 WorkBuddy 会话的连接器列表里只有 GitHub，
会话层面没有挂载 `mcp__mcd-mcp__*` 工具。

**决策**：项目自身通过 `@modelcontextprotocol/sdk` 的
`Client` + `StreamableHTTPClientTransport`，在 Next.js 服务端建立连接。

**理由**：
1. 项目必须能独立运行，不能把"能否调用"绑在某个 AI 会话的连接器状态上；
2. token 只在服务端，天然符合"不把 token 交给浏览器"的要求；
3. 官方 SDK 支持超时、AbortSignal，便于做健壮性处理。

**代价**：每次进程冷启动要重新握手（约 300–600ms），已用 `globalThis` 缓存单例缓解。

## ADR-002 金额一律用整数「分」

**背景**：两个上游接口的单位不一致 ——
`query-meals` 返回元字符串（`"25.5"`），`calculate-price` 返回整数分（`2250`）。

**决策**：领域模型只存 `priceFen: number`，元只在展示层出现。
`yuanToFen()` 用字符串逐位解析，不用 `parseFloat(x) * 100`。

**理由**：预算累计是核心场景，浮点误差会直接体现为"算出来比实际多一分钱"这类诡异 bug。
`assertFen()` 还会在算价接口口径变化（返回小数）时立刻抛错，而不是静默出错。

## ADR-003 营养数据不与菜单 SKU 关联

**背景**：`list-nutrition-foods` 只有 `productName`，菜单是 `code` + `name`，两者无可靠的公共键。

**决策**：`MealItem.nutrition` 恒为 `null`；营养数据由 `listNutrition()` 单独返回，不做 join。

**理由**：任务书明确禁止"通过不可靠的名称猜测生成营养数据"。名称匹配会在
"麦辣鸡翅-2块" / "麦辣鸡翅" 这类近似名上给出错热量，对饮食推荐是实质性错误。
未来若上游补 `code`，再在 `MealItem.nutrition` 填值。

## ADR-004 解析 `list-nutrition-foods` 的表格字符串

**背景**：该接口的 `data` 不是数组，而是一段紧凑表格字符串：

```text
[160]{productName,nutritionDescription,energyKj,energyKcal,protein,fat,carbohydrate,sodium,calcium}:
  猪柳麦满分,null,1288,308,16,16,24,781,213
```

**决策**：写 `parseNutritionTable()` 按表头解析列名，逐行切分；
`null` / 空串 → `undefined`（不填 0）；缺 `energyKcal` 的行直接丢弃。
同时保留数组分支，兼容上游未来改结构。

**理由**：如果不解析，这个能力等于不可用（第一次集成测试就是因此失败：期望 >100 条，实际 0 条）。

## ADR-005 首页不在 Server Component 里连 MCP

**决策**：首页静态渲染，MCP 状态由客户端组件 `McpStatusBadge` 异步 fetch `/api/health`。

**理由**：
1. 构建期不需要外网，`next build` 稳定；
2. 首屏秒开，不会因为上游握手 500ms 而白屏；
3. 连接状态本来就是"运行时信息"，不适合烤进静态页。

`/api/health` 则用 `await connection()` 强制动态执行（见 ADR-006）。

## ADR-006 Next 16 `cacheComponents` 下不能用路由段配置

**背景**：`create-next-app@16.4.2` 生成的 `next.config.ts` 默认开启
`cacheComponents: true` 与 `partialPrefetching: true`。

**问题**：最初在 `app/api/health/route.ts` 写了：

```ts
export const runtime = "nodejs";
export const dynamic = "force-dynamic";
```

构建直接失败：

```text
Error: Route segment config "dynamic" is not compatible with `nextConfig.cacheComponents`. Please remove it.
Error: Route segment config "runtime" is not compatible with `nextConfig.cacheComponents`. Please remove it.
```

**决策**：删掉两个段配置，改为在 handler 开头 `await connection()`（来自 `next/server`）。

**理由**：这是 Next 16 在 cacheComponents 模式下的官方写法，等价于"每次请求动态执行"。

## ADR-007 去掉 `next/font/google`

**决策**：删除脚手架的 Geist 字体加载，改用系统字体栈，并在 `globals.css` 锁定浅色配色。

**理由**：
1. `next/font/google` 在**构建期**下载字体，离线/受限网络会让 `next build` 失败；
2. 项目没有深色模式需求，保留 `prefers-color-scheme: dark` 会导致"深底深字"不可读。

## ADR-009 测试目录拆三步（fixtures / unit / integration）

**决策**：`tests/fixtures` 放真实抓取返回，`tests/unit` 不联网，`tests/integration` 连真实 MCP。

**理由**：
- 单测必须能离线跑、可重复；
- 但归一化逻辑又必须用**真实结构**验证，手写假数据容易把错误结构测成"通过"；
- 集成测试没 token 时整组 skip，报告里记"未验证"，不拿 mock 冒充真实结果。

## （任务 002）ADR-010 先定"餐品角色"，再谈预算

**背景**：任务书要求不能拿酱料、纪念品、单独饮料冒充一顿完整正餐。真实菜单里 123 项
SKU 中只有 63 项能算"一份正餐"，剩下 60 项是饮料 23 / 配餐 19 / 甜品 8 / 周边 5 / 多人餐 4 / 酱料 1。

**决策**：`classifyItem()` 先按关键词定角色（combo/main/side/drink/dessert/sauce/merch/unknown），
只有 `combo` 与 `main` 能当"锚点"；`side`/`drink` 只能作为加购项参与 `main+side` / `main+drink` 组合。

**理由**：如果按价格排序再取最低价，第一个被选中的永远是 ¥3 的「韩式烟熏芝士风味酱」。
角色先行，价格才有意义。

**代价**：关键词启发式会漏判新造词（落到 `unknown` 不推荐）。选择"宁可不推"而不是"猜着推"。

## （任务 002）ADR-011 菜单价只做粗筛，结论必须来自 calculate-price

**决策**：预算过滤用菜单标价做一次粗筛（减少算价调用），但**最终输出必须经过 `calculate-price`**；
两者不一致时以算价为准并置 `priceMismatch: true`；算价抛错就跳过该候选，绝不用标价顶上。

**理由**：菜单标价是展示价，算价才是这一单的真实应付。用标价冒充核验结果，等于把
"未验证"包装成"已验证"，这是本项目最不能接受的一类错误。

## （任务 002）ADR-012 评分权重是实测调出来的，不是拍脑袋

**记录两次真实修正**：

1. 省钱方案最初 `preference: 0.10`，真实跑出来「¥15.90 鸡薯双全盒（命中鸡肉）」压过
   「¥13.90 随心配」——叫"省钱优先"的方案多花 2 元。把偏好权重降到 0.02 后恢复语义。
2. 均衡方案最初纯按权重算，真实跑出来是「¥17.00 单点麦香鸡」，等于又一个省钱方案。
   改为**先试"组成完整"的候选（套餐/主食+配餐），试不到才退回单主食**（`prioritizeComplete`）。

**理由**：仅靠权重无法表达"均衡至少要有个套餐"这种硬偏好，硬偏好用排序分层表达更诚实，也更好解释。

## （任务 002）ADR-013 营养维度不参与打分（延续 ADR-003）

**决策**：评分函数只有四个维度（priceFit / completeness / preference / value），没有热量/营养；
`MealItem.nutrition` 恒为 `null`；"均衡选择"的文案里写死"这不是营养判断"。

**验证**：单测里强行往候选塞入 `nutrition` 数据，断言得分**完全不变**——用测试守住这条边界。

## （任务 002）ADR-014 门店查询失败降级而不是报错

**决策**：`query-nearby-stores` 失败/查不到时，不阻断推荐流程，只降级为"门店名留空 + `warnings` 告警"，
因为 `storeCode` 由调用方给出，菜单与算价都不依赖门店名。

**例外**：`MISSING_TOKEN` / `TIMEOUT` / `CONNECT_FAILED` 视为上游整体不可用，直接抛错——
这时候继续跑下去只会把所有候选都算成"失败"，不如快速失败给前端一个准确状态。

## （任务 002）ADR-015 限流用进程内实现，并写明它的边界

**决策**：`lib/api/rate-limit.ts` 用 `globalThis` 上的滑动窗口（20 次/分钟/IP），不引入 Redis。

**理由**：本期是单机参赛版本，引入外部存储会扩大部署面。但**必须在代码注释和报告里写清**
"多副本时各算各的，挡不住总量"，否则使用者会高估这层保护。

## （任务 003）ADR-016 日期用「纪元日序号」，禁用 `Date` 加减

**背景**：预算周期天然跨月、跨年（12-20 ~ 01-10），还要处理闰年与"用户时区里的今天"。

**决策**：`DateKey = YYYY-MM-DD` 是唯一日期形态；所有加减/差值都换算成
`epochDay = Date.UTC(y, m-1, d) / 86400000` 做整数运算。时区只在 `dateKeyOfInstant()` 一处出现。

**理由**：
- `new Date(2026, 0, 31).setMonth(1)` 会得到 3 月 3 日；
- 用毫秒累加 `addDays` 在夏令时地区会差 1 小时，跨午夜就错一天；
- 服务端 UTC + 客户端东八区，「今天」会差一天，必须显式指定时区。
  实测：`2026-10-31T16:30Z` 在上海是 11-01（出周期），在 UTC 是 10-31（在周期）——时区选错就会漏记/多记。

## （任务 003）ADR-017 `planned` 与 `confirmed` 物理隔离，推荐永不自动入账

**决策**：`ExpenseRecord.status` 只有 `planned / confirmed`；概览的"已花金额"**只**统计 `confirmed`；
`planned` 只进入 `plannedImpact`（前瞻）。推荐结果只生成"消费草稿"，写账本必须用户点确认。

**理由**：任务书明确禁止"点推荐就扣预算"。把"可能发生的钱"和"已经花掉的钱"混在一个字段里，
任何一次误触都会污染账本，且用户事后无法区分。分开存 = 可撤销、可解释、可审计。

**代价**：界面上多一个"计划中"状态和"确认为已消费"按钮，属于必要的复杂度。

## （任务 003）ADR-018 预算计算全部放在客户端纯函数，不做服务端接口

**决策**：`lib/budget/*` 全是纯函数，被 `/budget` 页面直接调用；**不新增** `POST /api/budget/*`。

**理由**：
- 数据本来就在 localStorage，服务端拿不到，除非把用户账本上传（与"无账号、无云同步"冲突）；
- 纯函数可以被单测直接覆盖（270 项里的 117 项），比"测 HTTP 接口 + 靠日志猜"更可靠；
- 只有纯函数能保证"页面上看到的数字"和"测试里的数字"是同一份代码算的。

**代价**：将来若要做跨设备同步，需要把同一份纯函数搬到服务端复用（现在就是为此设计的，无 IO 依赖）。

## （任务 003）ADR-019 「今天是否被这一笔覆盖」必须显式化

**背景**：任务书样例的口径是"今天这顿已覆盖 → 后续只剩 11 个完整预算日"，
但同一份逻辑如果默认成立，用户今天还想吃第二顿时就会算错；
更隐蔽的是：`planned`（计划支出）如果也按"覆盖今天"算，`plannedFen=0` 时日均都会虚高。

**决策**：`computeMealImpact` 增加
- `mealsLeftToday`（含本次，默认 1）
- `otherMealsTodayFen`（今天其它餐费）
- `assumeCoversToday`（显式覆盖推断，优先级最高）

`BudgetSummary.plannedImpact` 固定传 `assumeCoversToday: false`。

**理由**：这个假设直接决定分母是 `daysRemaining` 还是 `daysRemaining - 1`，差一天就是百分之几的误差。
把它变成显式参数，等于把"预测口径"写进 API 契约，界面上也能让用户自己选"今天还剩几餐"。

## （任务 003）ADR-020 建议单餐预算「宁可不给，也不给假数」

**决策**：`suggestMealBudget()` 向下取整到整元；若低于 API 下限 500 分（¥5），
返回 `suggestedFen: null` + `blockedReason`，而不是"夹到 ¥5 让请求能发出去"。

**理由**：夹到下限等于用"能查到的数"冒充"应该花的数"——用户会以为系统建议他花 ¥5。
同理，已超支 / 周期结束时也返回 null，界面上明确写"仍可手动指定单餐预算去查询"。

## （任务 003）ADR-021 localStorage：版本号 + 逐条容错 + 级联删除

**决策**：
- 信封 `{version: 1, ...}`；版本不认识（无论新旧）→ **整份拒绝读取**，不用猜测的方式迁移；
- 单条计划/记录坏了 → 只丢那一条，并生成 issue 让界面提示（一条脏数据不该毁掉整份账本）；
- 重复 id → 保留 `updatedAt` 最新的一条；指向不存在计划的记录 → 跳过并计数；
- 删除计划 → 级联删除其记录；清空数据 → 显式二次确认。

**理由**：localStorage 的写入可能被中断（用户关页面）、可能被手动改、可能被旧版本写过。
"宁可空账本也不要算错钱"是这里唯一的原则；而"逐条容错"是避免用户因为一条脏数据失去整月记录。

## （任务 003）ADR-022 需要进一步选择的套餐，金额必须留空

**决策**：`draftExpenseFromRecommendation()` 在
`needsFurtherSelection === true` 或 `priceVerified === false` 时返回 `amountFen: null`，
强制用户填写实付金额（界面把输入框留空并说明原因）。

**理由**：随心配 / 1+1 的官方算价只是"起价"，组成未定就当作最终消费金额，会把预测与实际拉开差距；
而"未核验的菜单标价"更不该冒充实付。E2E 里专门用 ¥14.90 覆盖 ¥13.90 验证了这条路径。

## （任务 004）ADR-023 大模型只产出「意图」，不产出任何数据

**决策**：`ParsedIntent` 的类型里没有任何价格、餐品、优惠券、营养字段；
`intent-schema.ts` 的 `LLM_INTENT_KEYS` 白名单也不包含它们。模型即便在 JSON 里塞
`priceQuote` / `recommendedDish` / `nutrition`，也会被 `normalizeLlmPayload` strip 掉，
并记入 `ignoredFields` 供审计。

**理由**：任务书禁止"由大模型自行生成未经验证的餐品价格、优惠券金额或营养数据"。
与其在提示词里反复叮嘱（模型可能不遵守），不如让类型系统上根本没有这个位置——
"编不出来"比"被要求不要编"可靠得多。价格只有一条来源：`calculate-price`。

**代价**：意图与数据之间需要一次显式拼装（`response-builder`），比"让模型一次吐出全部"多写代码。
这是值得的，因为拼装过程本身可测试、可断言。

## （任务 004）ADR-024 排除项进过滤层，不进评分层

**决策**：`RecommendRequest.avoidTags` 传给 `filterMenu` 的 `excludeTags`，
在**餐品角色分流之前**做确定性剔除；`ExclusionReason` 新增 `"excluded_tag"`。
被排除的餐品不会进入候选池，因而也不会触发 `calculate-price`。

**理由**：（1）任务书明确要求"不能只通过低分惩罚"——打分是相对的，只要其它候选更差，
被排除的餐品仍可能被选中；（2）放在分流之前是为了让加购项也一起排除，否则
"最便宜的主食 + 最便宜的配餐"里的配餐很可能正是被排除的那一个；
（3）不发起算价还能省上游调用次数。

**验证**：造一份全是辣味的菜单，排除「辣」后 `quotePrice` 调用数为 0。

## （任务 004）ADR-025 预算只能被下调，不能被上调

**决策**：`resolveBudget()` 的来源优先级为
「用户这次说的 > 长期预算建议值 > 上下文硬上限 > 默认 ¥25」，
选定后再依次被「用户已设的单餐上限」与「接口区间 ¥5~¥200」夹一遍。
**任何一条路径都不会让最终预算大于用户已设的硬上限**；
因上下文被下调时置 `clampedByContext`，因接口区间被调整时置 `clampedByApiLimit`。

**理由**：自然语言是最容易被"越权"的入口——用户随口一句"50 块也行"不应该覆盖他自己设的
¥25 上限，模型幻觉出的金额更不应该。只有"下调"是安全的，因为下调的后果是"少花钱"。

**例外**：低于接口下限（¥5）时**不做推荐**，先要求澄清，而不是夹到 ¥5 硬推——
否则等于用系统下限覆盖了用户说的"我只有 3 元"。

## （任务 004）ADR-026 提示注入：命中就不调用模型

**决策**：`detectInjection()` 用一组确定性正则识别
「忽略以上指令 / ignore previous instructions / system: / 输出你的提示词 / 密钥 / </user_input> / 帮我直接下单支付」
等特征。命中后**根本不把文本发给模型**，直接走规则通道，并返回
`INJECTION_SUSPECTED` 告警；文本里夹带的正常条件仍然按规则解析出来。

**理由**：提示注入的防御不该建立在"模型足够听话"上。最可靠的隔离是**不把污染源接进来**。
另外，输入里的"下单/支付"请求本来也不可能被执行——`lib/ai` 里没有这类工具，
拦截只是把"做不到"变成"明确告知做不到"。

**副作用**：极端情况下正常用户写了"帮我直接下单"也会被降级到规则模式。
考虑到本产品本来就不下单，这个代价可以接受（规则模式一样能给出推荐）。

## （任务 004）ADR-027 模型故障不产生错误码，只降级

**决策**：`parseIntent()` 永不抛错。无 Key、超时、HTTP 错、JSON 不合法、Schema 不通过，
一律返回 `mode: "RULE_FALLBACK"` + `ai.fallbackReason`，请求继续走真实菜单与算价。
只有"输入不合法"和"上游 MCP 出错"才会产生 HTTP 错误码。

**理由**：AI 是**增强**而不是**前置依赖**。让模型的一次超时变成"用户今天点不了饭"，
是把可用性绑在一个外部服务上。降级后能力确实变弱（只认有限条件），所以必须
在接口与界面上把"现在是规则模式"说清楚——降级可以，冒充不行。

## （任务 004）ADR-028 免责说明是一等公民，不做折叠

**决策**：
- 只要用户提了排除项，`caveats` 必定包含 `exclusionCaveat()`，且 `warnings` 必定包含
  `EXCLUSION_NOT_GUARANTEED`；文案固定出现"按菜单名称关键词""无法保证绝对不含""点单时请再确认"；
- 提到过敏时必定包含 `ALLERGEN_CAVEAT`（"无法确认""不能保证食用安全"）；
- 每次响应都带 `PRICE_CAVEAT` 与 `MEDICAL_CAVEAT`；
- 前端把 `caveats` 与 `warnings` 直接铺在结果下方，**不放进 `<details>`**。

**理由**："不能宣称绝对不含"这类要求，如果只写在代码注释里、界面上却折叠起来，
等于没有落实。测试用正反双向断言守着：正向必须含"无法保证"，反向不允许出现绝对化承诺
（检测时显式剥离否定句式，避免免责说明被误判）。

**代价**：结果区变长。但这部分内容恰好是"用户做决定前必须知道"的，长一点是应该的。

## （任务 004）ADR-029 用户带来的预算上下文按不可信输入处理

**决策**：`context.budget` 必须带 `authorized: true` 才被采纳；即使带了，
也按不可信输入重新校验：只接受整数（`3.5` 天直接丢弃，不四舍五入）、
金额有上下界、城市/关键词截断到安全长度。
**AI 层没有任何写入口**——不写账本、不改预算、不删记录，`lib/ai` 里连账本写函数的引用都没有
（有静态扫描测试守着）。

**理由**：浏览器传来的数字可以被用户任意修改，把它当"账户余额"信任，会把一个本地记账工具
变成"可以伪造余额的系统"。同时，"这个月还剩 300 元"这类表述只作为提示写入
`remainingMentionFen`，绝不落账——账本只能由用户在预算页手动改。

## （任务 004）ADR-030 不绑定模型供应商，也不假设结构化输出

**决策**：业务层只依赖 `LlmProvider` 接口；默认实现走 OpenAI 兼容的 `chat/completions`。
默认**不发送** `response_format`（只有显式 `AI_JSON_MODE=1` 才发），改为
"提示词要 JSON + `extractJsonObject()` 宽容提取 + Zod 严格校验"三件套。
配置项：`AI_API_KEY` / `AI_BASE_URL` / `AI_MODEL` / `AI_TIMEOUT_MS` / `AI_JSON_MODE`。

**理由**：不同供应商对 JSON mode 的支持程度不同，把正确性押在供应商特性上会导致
"换一家就不能用"。宽容提取 + 严格校验的组合对任何供应商都成立，代价是要处理
JSON 代码围栏与前后废话——`extractJsonObject` 已经覆盖（含字符串内花括号）。

**顺带**：`AI_BASE_URL` 可以写成 `https://host/v1` 也可以写完整 `.../chat/completions`，
方便对接不同形态的网关。

## （任务 004-A）ADR-031 否定判断用「否定窗口」，不用紧邻正则

**决策**：在既有的紧邻规则（`不吃辣`、`不要牛肉`）之外，再加一层**否定窗口**：
否定词之后 **0~6 个非断句字符**内出现品类提及，即判为排除；窗口**不允许跨过**
逗号、句号、顿号与空白。

**理由**：验收实测「不想吃昨天吃过的汉堡，换个口味」被解析成了「想吃汉堡」，
推荐里真的出现了汉堡——紧邻正则对这种插入语无能为力，而这是最危险的一类错误
（把用户的"不要"读成"要"）。窗口取 6 而不是更大：`不想吃昨天吃过的汉堡` 中间正好 6 字，
而 `不想花太多来个鸡肉` 中间是 7 字——再放宽就会把用户**想要**的东西误判成排除，
那种错误比漏排更伤体验。跨逗号/空白不允许，是为了让「不想吃汉堡，想吃鸡肉」这种
并列句两边各自成立。

**代价**：更长的插入语（如"不想吃昨天吃过的那个汉堡"）会漏，由「换一种」历史规则兜一层；
单说不换时会漏——已记入已知问题。

## （任务 004-A）ADR-032 期望价位与硬上限分开存，不能互相吞掉

**决策**：`ParsedIntent` 新增 `preferredFen`。「20 元左右，但绝对不能超过 25 元」
解析为 `budgetKind=hard_cap` + `budgetFen=2500` + `preferredFen=2000`；
预算裁决取 `applied = min(preferred, hardCap)`，`hardCapFen` 保留原话 2500。

**理由**：修复前只保留 25，结果「满足优先」给到 ¥22.90——既不符合"20 左右"的期望，
又让用户以为系统只听到了上限。两个数字是两件事：一个是**想花多少**，一个是**不能超过多少**，
合并成一个字段必然要丢掉其中一个语义。

**边界**：只有 `preferred < hardCap` 时才采纳 `preferred`；`大概 30 左右，但不超过 20`
这种矛盾表述不采纳期望值，只按 20 的硬上限走。

## （任务 004-A）ADR-033 用户说的金额绝不"上调"，钱不够就说钱不够

**决策**：`hardCapFen` 取用户原话的金额（而不是被夹到接口下限后的值）；
金额低于平台最低可查询金额时：不发起查询、不给任何推荐、`emptyReason` 写明
"低于平台可查询的最低金额"，并**抑制**"预算已调整到 ¥5.00"这类告警。

**理由**：修复前「我只有 3 块钱」的响应里写着 `hardCapFen: 500` 和"预算已调整到 ¥5.00"，
等于替用户把预算改大了 67%。既然本次压根不查询，就不该出现任何暗示"按 ¥5 找"的文案。
内部 `appliedFen` 仍保留 ¥5.00（引擎的最小可查询单位），但它不再对外冒充用户的预算。

## （任务 004-A）ADR-034 系统没有历史记录这件事，要写在响应里

**决策**：用户提到"昨天/上次吃过什么"时，`ParsedIntent.historyTags` 记录该品类
（仅来自这一句话），响应固定追加一条 caveat 与 `HISTORY_NOT_RECORDED` 告警：
"系统没有你的历史用餐记录，也没有去读任何记录"。同时用静态断言禁止响应里出现
"根据你的历史（记录/订单/消费）"。

**理由**：系统确实没有历史数据——不读账本、不读订单、没有云端画像。如果只是默默
按这句话排除，用户很容易以为"它记得我昨天吃了什么"。**能力边界必须由系统主动说出**，
而不是等用户发现。预算上下文同理：账本可能漏记，所以口径统一为
"根据你已记录的消费估算"，并提示漏记会让实际更少（`LEDGER_ESTIMATED`）。

## （任务 005）ADR-035 颜色只有一个来源，且官方色值写进测试

**决策**：全站颜色只在 `app/globals.css` 的 `:root` 里定义一次，通过 `@theme inline`
映射成 `--color-brand-500` / `--color-ink-500` 这类 Tailwind 语义类；
约定组件里只写语义类名、不写裸十六进制色值（现状：`components/` 与三个页面里
零处裸色值，唯一例外是 `app/page.tsx` 里用 `var(--brand-100)` 画的高亮笔）。
同时 `tests/unit/ui-design-system.test.ts` 静态断言样式表中**不含**
`#DA291C`、`#FFC72C`、`#FFBC0D`。

**理由**：项目用麦当劳官方 MCP 拿真实菜单与算价，但产品不是官方产品。视觉上
如果贴近官方红黄，会被误认为麦当劳自家的应用——这是**身份风险**，不是审美问题。
把它写进测试而不是写进设计规范的原因很实际：规范文档没人执行，测试会失败。

**代价**：主色比官方红要"淡"一些，第一眼的冲击力弱于红黄配色；换来的是
一眼能区分「这是第三方工具」。

## （任务 005）ADR-036 三份方案不是等权三卡，首选必须"更大、更前、更像答案"

**决策**：`balanced` 方案作为**首选**：整行宽、顶部品牌渐变条、
`lg` 断点双栏（左「吃什么与为什么」/ 右「钱怎么变」）、理由全文 + 全部 fitNotes；
另两份为**备选**：`md:grid-cols-2` 两栏、compact、只保留 2 条 fitNotes。
`primary: true` 由引擎给出，UI 不自己判断。

**理由**：任务书要求"优先突出符合主要目标的首选方案，其余两张为替代"。
等权三卡会让用户在三个选项之间反复比较，反而更慢——这与"30 秒完成一次推荐"
直接冲突。差异必须体现在**版面权重**上（宽度、留白、信息量），而不是只加一个
小小的"推荐"标签。首选卡右栏刻意 `self-start`，因为它比左栏短，
拉伸等高会让"钱怎么变"那块看起来空。

**代价**：首选卡信息密度高，移动端纵向更长（390 档首选+备选约 2.5 屏）。

## （任务 005）ADR-037 演示模式是独立路由 + 构建期常量，不是"出错时切过去"的分支

**决策**：`/demo` 是独立路由，数据来自 `lib/demo/sample-decision.ts`（一次真实
`/api/ai/decide` 响应被原样冻结成 `as const` 常量）。该路由**不 import**
任何 fetch 逻辑与首页交互组件，静态预渲染（构建产物中为 ○ Static）。
真实模式的错误处理里**没有任何**跳转到 `/demo` 的分支。
三道静态断言（`ui-demo-mode.test.ts`）守这三条。

**理由**：演示模式最容易出的错不是"演示数据不好看"，而是
"用户在真实模式查失败，页面悄悄给了一份好看的假结果"——那一刻产品就在撒谎。
把演示做成独立路由、独立数据、零网络请求，物理上就不可能发生这种回退；
而不是靠"记得写 if"来保证。冻结数据而不是 mock 生成：mock 会随代码演进而
与现实脱节，冻结的真实响应至少曾经是真的，页面只要说清"抓取时间"就诚实。

**代价**：菜单调价后 `/demo` 的价格会漂移，页面必须显式写明"不是实时查询"。

## （任务 005）ADR-038 错误文案分两层：给用户的一句话，给开发者的一行码

**决策**：`lib/ui/api-error.ts` 把错误码映射成 `{ title, hint, code, retryable }`：
8 类预设（`RATE_LIMITED` / `MCP_TIMEOUT` / `MCP_UNAVAILABLE` / `MENU_UNAVAILABLE` /
`STORE_UNAVAILABLE` / `MISSING_TOKEN` / `INVALID_REQUEST` / `INTERNAL`），
未知码按 HTTP 状态兜底（429/503/504/502/400/5xx）。
服务端返回的 `detail` 经过 `sanitizeDetail()`：抹 `Bearer …`、抹 32 位以上不透明串、
压空白、截断 120 字，再作为括号补充附在 `hint` 后面。
界面上：`title` 大字、`hint` 一行、原始 `code` 用 11px `ink-400` 小字。

**理由**：用户看到 `MCP_TIMEOUT` 只会觉得产品坏了；看到「门店数据这次没赶上，
没有用任何猜测数据顶替」才知道**下一步该做什么**，同时得到最重要的那句承诺。
把 `code` 保留在小字里，是为了截图/反馈时能定位，又不污染主文案。
脱敏放在**渲染前**而不是"记得别显示"：detail 来自上游，不可信。

**代价**：文案是硬编码中文，多语言要再抽一层（当前不在范围内）。

## （任务 005）ADR-039 文案当契约用测试锁住，而不是写在设计稿里

**决策**：`tests/unit/ui-copy.test.ts` 把四类文案变成断言：
① 首屏必须有 H1 三段、副标题、主按钮、placeholder、4 个场景；
② 首屏（从 `return (` 起截取）不得出现 `query-meals` / `calculate-price` / `traceId` / `MCP`；
③ 全站不得出现「正在使用大模型」这类冒充，必须出现「为什么不是大模型解析」；
④ 全站必须出现「不能保证绝对不含」（排除项的边界）。
另有客户端组件不得引用 `AI_API_KEY` / `MCD_MCP_TOKEN` / `AI_BASE_URL`、不得出现 `mcp.mcd.cn`。

**理由**：任务书 §4/§5 的文案要求非常具体（连 placeholder 的原话都给了）。
设计规范文档改一次就漂一次，测试不会。特别是 ③④ 两条——它们是**诚实性约束**，
一旦有人为了"看起来更智能"改个词，产品就开始撒谎了，这种回归必须被机器拦住。
②（首屏不带术语）用截取 `return (` 之后的源码来判定，而不是渲染后文本，
是为了避免把 `<details>` 里的技术说明误判成首屏内容。

**代价**：改文案要先改测试，轻微增加改动摩擦——这是有意为之。

## （任务 005）ADR-040 构建清理不删 `.next`，只挪成带时间戳的备份

**决策**：本机 safe-delete 保护会拦截 Next 清理 `.next`（>50 文件）。处理方式固定为
`mv .next .next.bak-<任务号>`，**不执行任何删除**；备份留在盘上由人工决定何时清理。
`.next.bak-*` 目前**未被** `.gitignore` 覆盖，发布前必须补（见报告 §8 R1）。

**理由**：上一轮曾因"删东西"造成误解，此后约定：除自己刚生成的临时文件外，
任何删除先问。构建产物是最容易被顺手清掉、又最容易被误认为"源码被动了"的东西，
所以对它的策略是**只增不减**。

**代价**：每次构建留 ~60MB 备份，本次三个备份共约 178MB。已在报告的发布前
风险清单里列为必须处理项。

## （任务 006）ADR-041 「只挪不删」的产物必须同时被忽略

**决策**：只要采用「构建产物只挪不删」的策略，`.gitignore` 就必须同步覆盖挪出来的名字
（`/.next.bak-*/`）。两者是**同一件事的两半**，不能只做一半。

**理由**：任务 005 结束时留下 `.next.bak-005/005b/005c` 共 178MB，而 `.gitignore` 只写了
`/.next/`。这意味着「不删文件」这个出于谨慎的决定，会直接变成「把 178MB 构建垃圾提交进公开仓库」。
审计时用 `git check-ignore -v` 逐条验证，而不是靠肉眼读 `.gitignore`——
规则写没写对，是 `git` 说了算，不是读起来像不像。

**教训**：任何"留一手"的操作（备份、临时文件、日志）都要问一句「它会不会被提交」。

## （任务 006）ADR-042 测试断言不变量，不断言实时数据的当日快照

**决策**：涉及真实上游数据的断言，只允许写**不变量**：
预算内的方案必须 `priceVerified`、给不出必须给 `emptyReason`、所有价格 ≤ 预算；
**禁止**写「今天菜单里一定没有 ¥10 内的正餐」「一定返回 3 份」这类**当日事实**。

**理由**：任务 006 首跑集成测试就红了一条——2026-10-22 门店上架 ¥9.90 的「芝芝火腿扒堡组合」，
于是「10 元预算必然返回 0 条」当场失效。产品没错，是断言的**假设**过期了。
同理，E2E 写死 `cards === 3`，遇到 ¥18 预算只给 2 份（引擎「不做凑数」）时也红了。
这类失败最危险的地方在于：**它看起来像产品坏了**，会诱使人去改产品而不是改测试。

**代价**：断言变"松"了一点，不再能捕捉"份数从 3 掉到 2"这种变化。用另一条更强的断言补回来：
方案标题必须都在 `{省钱优先, 均衡选择, 满足优先}` 集合内——数量可以变，**语义不能变**。

## （任务 006）ADR-043 界面里的「份数」必须来自数据；「请求」与「事实」要分开

**决策**：凡是陈述事实的文案（如分区标题「另外两份备选」），份数必须由 `alternatives.length` 生成；
凡是表达用户意图的文案（如按钮「按预算帮我挑三份」），可以保留固定措辞，但结果页必须**解释差异**
（引擎已有 `INSUFFICIENT_CANDIDATES`：「预算内只找到 2 份…不做凑数」）。

**理由**：同一类"3"，性质不同。标题写「两份备选」而实际只有一份，是**撒谎**——用户会怀疑页面渲染坏了；
按钮写「帮我挑三份」而只给两份，是**许愿没实现**——只要有解释就是诚实的。
两者用同一把尺子处理（要么都改、要么都不改）反而都不对。

**连带修复**：只有 2 份方案时 `md:grid-cols-3` 会在右侧留一个空洞。栅格也要跟着份数走，
否则"少了一份"看起来像"渲染失败"。

## （任务 006）ADR-044 仓库初始化有前置门禁，且只做 `git init`

**决策**：`git init` 之前必须确认三件事——① 工作区就是项目根、无杂项文件；
② 忽略规则对 `.env*` / `.next.bak-*` / `node_modules` / `*.tsbuildinfo` 全部生效（`git check-ignore -v` 实测）；
③ 敏感文件清单完整、且已用**真实 token 反查**确认零泄露。
之后**只做 `git init`**：不 `add`、不 `commit`、不建远端、不推送。

**理由**：仓库一旦有了提交，"误提交的密钥"就变成"历史里的密钥"，清理成本陡增。
所以顺序必须是「先证明干净 → 再建仓库 → 再由人决定第一次提交」。
本次审计的 `git init` 是在三项确认全部通过后执行的，结果：`main` 分支、0 提交、0 远端、154 个未跟踪文件、7.17MB。

## （任务 006）ADR-045 许可证不擅自选定，但把兼容性算清楚

**决策**：审计只做**候选分析**（MIT / Apache-2.0 / AGPL-3.0 / 暂不添加），
给出依赖侧的兼容性结论，但**不创建 `LICENSE` 文件**——选许可证是法务与参赛规则的判断，不是工程判断。

**理由**：许可证一旦加上就极难撤回（已经有人按它用了）。另一方面，不审计也不行：
用 30 秒扫完 162 个依赖的许可证，能立刻排除"引了 GPL 却想用 MIT"这种致命错误。
实测结果：MIT 136 / ISC 10 / Apache-2.0 6 / BSD-3 3 / MPL-2.0 2 / LGPL-3.0(or later) 2 / CC-BY-4.0 1，
**零 GPL/AGPL/SSPL**，因此 MIT 与 Apache-2.0 都兼容；MPL 是文件级 copyleft（不改就不触发），
LGPL 的 `sharp` 只在"分发二进制"时才需要附声明——当前只发源码，不构成义务。

**边界**：建议 MIT（生态同频、评审熟悉），但最终由人决定；决定的后果（是否与参赛规则一致）也在人这一侧。

## ADR-046 参赛声明不自行撰写，而是逐字使用官方原文

**背景**：任务书要求"准备 `CONTEST_DECLARATION.md`：原创性、合规性及敏感信息声明"，
字面理解像是"写一份声明"。但核对官方活动规则后发现，该文件被明确要求
**「文件名及内容均不可改动」**，并建议直接使用官方提供的文件。官方原文本身已覆盖
原创性声明、合规声明、信息安全声明、使用提示、规则遵守声明五项。

**决策**：逐字复制官方原文，**不做任何本地化改写**，不加注释、不加页脚、不加项目名。
落盘后做结构校验（5 个二级标题、末行文本），并用两次独立抓取交叉核对。

**理由**：这是"规则优先于任务书字面"的典型情形。自定义一份"看起来更完整"的声明，
会让报名校验直接失败；而失败原因（"内容被修改"）在报名期只有几天余量时非常昂贵。
加一行说明文字也属于修改，所以连"本文档由 XX 项目提供"这类话都不能加。

**代价**：文件无法体现项目个性，看起来"不像自己写的"——但这正是要求本身的目的（防抄袭、统一口径）。

**边界**：若官方后续更新该文件，应整体覆盖，而不是手工合并差异。

## ADR-047 许可证文本可以先落地，但版权主体不替人填

**背景**：开源发布必须有 `LICENSE`；但版权主体与年份是法务事实。

**决策**：`LICENSE` 放 MIT 标准文本，版权行写 `Copyright (c) 2026 [COPYRIGHT HOLDER]`，
并在报告与对话中**明确标注该文件在替换前不适合公开**，同时给出替换方法。

**理由**：全占位 0 字节等待，会让"发布"卡在一个纯行政动作上；但替所有者编一个名字，
是把法务风险伪装成工程完成度。两者的区别在于：占位符是**显式的未完成**，
编造是**隐性的错误**。前者可以被检查出来，后者不能。

**代价**：多了一个"必须人工替换"的门禁项（报告 §8 P0）。这是有意的——它就该被看见。

## ADR-048 首次提交用占位作者，推送前 amend

**背景**：仓库 0 commit，任何改动不可回滚；但 git 作者信息需真实姓名与 GitHub 邮箱才能
让提交关联到账号，而该信息属于所有者。

**决策**：本地提交使用 `Wen <wen@example.com>`（`example.com` 为保留域名，明确是占位），
**仅本地、不推送**，并在报告给出 `git commit --amend --reset-author` 的修正命令。

**理由**：0 commit 是当前最大的工程风险（改坏了无法回退），优先消除。
而作者信息在**推送前**完全可改，属可逆操作。先建立回滚点、后修正元数据，风险最低。

**代价**：若忘记 amend 就推送，公开历史里会留下占位邮箱。因此把它列为 P0 并在清单第 2 步强制出现。

## ADR-049 演示脚本只断不变量，不断当日菜单

**背景**：任务 006 已踩过一次坑——集成用例断言"10 元预算必然返回 0 条"，
结果当天门店真有 ¥9.90 组合，测试变红；E2E 断言"必须 3 份方案"，
¥18 预算只给 2 份（引擎明确 `INSUFFICIENT_CANDIDATES`），也变红。
两次都是**断言了当日事实**，而不是**业务不变量**。

**决策**：`scripts/demo-check.mjs` 的断言统一为不变量：
- 给得出方案 → 每份必须 ≤ 预算、必须 `priceVerified`；
- 给不出方案 → 必须有 `emptyReason` 或 warnings；
- 方案数量 1~3 均合法，不写死 3。

**理由**：真实数据源每天都在变，写死数量等于把"菜单今天恰好如何"当成产品契约。
一旦菜单变动，测试就红，人会开始怀疑产品而不是怀疑测试——这才是最坏的结果。

**代价**：断言强度看起来变弱（允许 1 份或 2 份）。但"允许数量变化、不允许语义缺失"
比"数量必须是 3"更接近真实业务约束：引擎的设计原则本来就是**宁可少给也不凑数**。

## ADR-050 工作区外的临时产物不进仓库

**背景**：任务 004～007 期间在工作区根目录产生了 `_e2e-005.mjs`、`_audit-006.mjs`、
`_t006/`、`_e2e-*.log`、`.chrome-e2e-*` 等调试产物，位于 `mealmate-ai/` 之外。

**决策**：这些**不进仓库**。转化为长期价值的部分才入仓：
- 三段演示的自查逻辑 → 重写为 `scripts/demo-check.mjs`（去掉了对 CDP/Chrome 的依赖，任何人可跑）；
- 凭证扫描思路 → 保留在 `docs/06` 与 `docs/07` 的方法描述里。

**理由**：审计脚本里含本机路径与扫描策略，E2E 脚本依赖特定端口与 Chrome 启动方式，
直接公开会让评委跑不起来。**能跑的脚本必须无副作用、无本机依赖**，
否则"可复现"只是口号。

**代价**：仓库里少了一份完整 E2E 脚本。已在报告 §5 如实标注 E2E 为"本地执行、脚本不入仓"，
没有把未公开的脚本算作公开可复现能力。
