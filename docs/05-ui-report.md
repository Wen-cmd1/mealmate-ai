## 1. 设计理念与视觉规范

### 1.1 从三个关键词到三条可检验的规则

任务书给的关键词是「有食欲、简洁、温暖、轻松、智能、可信」。这类词如果只写在文档里，落地时一定会走形，所以每个词都翻译成了一条可以拿工具检查的规则：

| 关键词 | 落地规则 | 可检查的证据 |
| --- | --- | --- |
| 有食欲 | 主色用**珊瑚橙**（`#F4713F → #DE5A2B`），底色调成**奶油白**（`#FFFCF8`）而不是纯白，让页面像纸而不像表格 | `ui-design-system.test.ts` 断言令牌存在且 `@theme inline` 映射齐全 |
| 简洁 | 首屏只有：徽标 → 大标题 → 副标题 → 输入框 → 4 个场景 → 主按钮。**技术细节全部下沉到页面底部**的 `<details>` | `ui-copy.test.ts` 断言首屏不出现 `query-meals` / `calculate-price` / `traceId` / `MCP` |
| 温暖 | 文字不用纯黑，用暖调墨色 `#2A211C`；阴影只在卡片与主按钮上出现 | `globals.css` 的 `--ink-900..400` |
| 轻松 | 圆角 14→22px 递进；大标题里「一句话」加一条手绘感高亮笔；动效只有 0.18s 的位移与透明度 | `app/page.tsx` 的 inline gradient 高亮 |
| 智能 | 「智能」不靠发光特效表达，靠**能解释自己**：入口显示解析模式、给 5 格条件回执、给「为什么不是大模型解析」 | `IntentSummary.tsx` |
| 可信 | 每张卡片都带**官方核验价**与核验状态、门店、数据边界；错误与限制分组但不折叠关键约束 | `ui-copy.test.ts` 卡片五要素断言 |

### 1.2 色板（唯一来源：`app/globals.css`）

```css
/* 主色：珊瑚橙 */
--brand-500: #f4713f;  --brand-600: #de5a2b;  --brand-700: #b8481f;
--brand-50:  #fff5ef;  --brand-100: #ffe3d4;  --brand-200: #ffc9ae;
/* 底色：奶油白 / 暖灰 */
--cream: #fffcf8;  --cream-deep: #fdf5ec;  --line: #efe4d8;
/* 文字：暖调墨色 */
--ink-900: #2a211c;  --ink-700: #4d4038;  --ink-500: #7c6c60;  --ink-400: #9d8d80;
/* 点缀：薄荷绿（只用于「已核验 / 安全 / 省钱」这类正向信号） */
--mint-500: #17a67c;  --mint-50: #e9f8f1;
```

**为什么不是麦当劳红黄**：`#DA291C` / `#FFC72C` / `#FFBC0D` 三个官方色值被静态测试**明令禁止**出现在样式表中（`ui-design-system.test.ts`）。选中珊瑚橙的理由不是审美偏好，而是**身份边界**：项目使用官方只读 MCP 拿真实菜单与算价，但产品本身不是麦当劳的官方产品，视觉上必须一眼可区分，否则参赛展示时会被误认为官方应用。

**品牌标记**：`components/ui/Brand.tsx` 里的 `BrandMark` 是自绘 SVG——一只碗 + 两缕热气，**不含任何官方商标、吉祥物或图片素材**。

### 1.3 字体与层级

| 层级 | 用法 | 规格 |
| --- | --- | --- |
| H1 | 首屏主标题 | `text-[30px] sm:text-[42px]`、`font-bold`、`tracking-tight`、`leading-[1.22]→[1.16]` |
| H2 | 区块标题 | `text-[17px] sm:text-[19px]` |
| 正文 | 说明文字 | `text-[14px]`、`text-ink-500` |
| 小字 / 元信息 | 门店、来源、traceId | `text-[11px]` ~ `text-[12px]`、`text-ink-400` |
| 金额 | 所有价格 | `.num`（等宽数字 + `tabular-nums`），`formatFen()` 统一出 `¥25.00` |
| 眉标 | `.eyebrow` | 11px 大写、`letter-spacing: .16em`、`ink-400` |

金额一律用 `formatFen` / `formatFenSigned` 渲染成等宽数字，避免 `¥25.00` 与 `¥9.10` 上下错位——这是价格类界面最容易露怯的细节。

### 1.4 圆角、阴影、动效（克制）

- 圆角：卡片 24px（`.surface`）、次级容器 18px（`.surface-muted`）、按钮 16px（`.btn`）、输入框 14px（`.field`）、胶囊 999px（`.chip`）。
- 阴影：`--shadow-card` 与 `--shadow-pop` 两档，**只有**卡片与主按钮使用，其余一律用 `--line` 描边。
- 动效：结果出现时一次 `.animate-fade-up`（0.34s，`cubic-bezier(.22,1,.36,1)`），别处不加。`prefers-reduced-motion: reduce` 下全部压到 0.01ms。
- 背景：`.page-glow::before` 两个低透明度径向暖光，出现在 `/`、`/budget`、`/demo` 三个页面的主容器上，给「暖」一个非文字的表达。

### 1.5 无障碍基线

- 全站 `:focus-visible` 统一焦点环（品牌色 2px + 2px 偏移），不用 `outline: none`。
- `app/layout.tsx` 有 `<a href="#main">跳到主要内容</a>`（`.sr-only`，聚焦时显形）。
- `aria-busy` 标在提交按钮、`aria-pressed` 标在场景 chip、`aria-current="page"` 标在页头导航、`role="alert"` 标在错误块、`role="status"` 标在加载与成功提示。
- `viewport` 使用 `maximumScale: 5` 而**不是** `user-scalable=no`（禁缩放是无障碍缺陷，静态测试会拦）。
- 移动端输入框字号 15~16px，避免 iOS 聚焦自动放大。

## 3. 关键交互流程

### 3.1 自然语言 → 推荐（主路径，目标 30 秒内完成）

```
首屏输入「今天只有 25 元，想吃鸡肉，不要太辣」
  → 点击「帮我选这一顿」（或 Ctrl/⌘+Enter）
  → 按钮进入 disabled + aria-busy，文案变「正在按官方价格核验…」
  → 骨架屏：三行文案说明正在做什么 + 两组占位卡
  → 结果区 scrollIntoView 到可见区，焦点交给结果标题
  → ① 条件回执（解析模式 / 餐次 / 预算·来源 / 目标 / 想吃 / 排除）
     ② 首选方案（满行、渐变条、双栏：组成与理由 | 本次预算·扣掉还剩·门店）
     ③ 「另外两份备选」（两栏 compact）
     ④ 数据来源条（query-meals · calculate-price · 耗时 · traceId）
     ⑤ 两个动作：「按这份再调条件」/「按这个金额记账」
     ⑥ 告警「需要你知道的几件事」+ 限制「数据边界与前提」（分组，不合并成一大段）
```

**防重复**：`if (loading) return` 在函数第一行拦截，配合按钮 `disabled` —— 两次点击只会产生一次请求。

**为什么不用自动滚动到顶**：结果区在首屏下方，用 `scrollIntoView({ block: "start" })` 让「首选方案」落在视口上部，用户不用手动找。

### 3.2 手动预算 → 推荐（第二条路，位置在自然语言之后）

首屏「另一种用法 · 或者，自己给一个单餐预算」→ 三个输入（预算 / 门店 / 偏好）→ 结果三张卡（省钱 / 均衡 / 满足）+ 数据来源条 + 告警分组。**位置刻意放在自然语言下方**：主路径应该是「说话」，表单是兜底。

### 3.3 长期预算 → Meal Impact

```
/budget
  → 英雄区：本周期还剩 ¥X（46px）+ 「根据你已记录的 N 笔消费估算…漏记的话实际更少」
    + 双进度条（实心=已用，竖线=时间进度）
  → 4 个 Tile：今日建议单餐预算 / 剩余预算天数 / 消费进度 / 后续日均可用
  → 「吃这顿之前 / 之后」：先一句人话
      「如果花 ¥78.00，接下来 9 天平均每天还能安排 ¥77.49。」
      再给 前(¥825.40 / ¥77.54) → 后(¥747.40 / ¥77.49, -¥0.05/天)
      底部：本次消费 / 占剩余 9% / 摊派 9 天
```

设计意图正是任务书那句**「让用户理解如果我今天花 25 元，接下来每天还能安排多少」**——所以结论句在数字对比**之前**，而不是让用户自己做减法。

### 3.4 推荐 → 确认金额 → 记账

首选卡底部「按这个金额记账」→ 带入金额到 `ExpenseComposer`（金额可改）→ 用户点「记为已消费」→ 写入 localStorage → 顶部 `Notice tone="good"`「已记为已消费」+ 预算数字同步刷新。

**严禁自动记账**（ADR-017 延续）：任何推荐结果**都不会**自动写入账本；`planned` 与 `confirmed` 在数据结构上就是两个字段，只有 `confirmed` 参与预算计算。本次 UI 重设计没有改动这条——它现在体现为「必须点一次带明确动词的按钮」。

### 3.5 演示模式（`/demo`）

- 顶部琥珀色横幅 `role="note"`：「这是演示数据，不是实时查询」。
- 元信息 `dl`：原始提问 / 抓取时间 / 门店 / 调用过的工具。
- 三张卡完整展示（复用真实卡片组件，但**不传** `onAdjust`，改为提示「演示模式：条件固定，不能重新查询」）。
- 底部「演示模式和真实模式差在哪」四条对比 + 跳转真实模式的按钮。
- 页面**零网络请求**：数据是构建期常量，静态预渲染（构建产物中 `/demo` 为 ○ Static）。

**三重隔离**：① 独立路由；② `lib/demo/sample-decision.ts` 不 import 任何 fetch/API 组件；③ 静态测试断言 `/demo` 目录不含 `fetch(`、不含 `/api/`、不含首页交互组件，且首页**不含**任何 demo 回退分支。

## 7. 视觉与交互遗留问题

诚实列出，未做粉饰：

1. **演示数据是冻结的**。菜单调价后 `/demo` 的价格会与门店实价产生偏差。这是刻意选择（页面已写明「不是实时查询」），代价是无法在无凭证环境下展示"刚刚查的"。**没有**做"重新抓取"按钮，避免演示页偷偷发请求。
2. **本次所有截图与 E2E 走的是规则解析路径**。`.env.local` 中未配置 `AI_API_KEY`，所以 `mode` 恒为 `RULE_FALLBACK`。大模型解析路径在任务 004-A 已用替身服务验证过（`_llm-mode-3101.json`），但**本次没有用真实模型密钥回归 UI**。若评审要求"展示大模型解析状态徽标为绿色"，需要先注入密钥再补跑一次。
3. **真实模式不会自动回退到演示**（符合 §9），因此现场断网/凭证过期时页面只有「数据未连通 + 重试」。演示的兜底方案是**手动**切到 `/demo`。
4. **排除项只匹配菜单名称，不读配料表**。「不要太辣」能过滤掉名称含「辣」的餐品，但配料含辣椒的商品不会被排除。界面已写明「不能保证绝对不含」，这是数据边界而不是实现缺陷。
5. **「均衡」不是营养均衡**。文案与卡片都明确写成"价格与组成"，未引入任何营养评分（ADR-003 / ADR-013）。如果评委按"营养均衡"理解会失望——这是**产品表述的取舍**，不是能力缺失的掩饰。
6. **移动端结果页纵向偏长**。390 档下首选卡 + 两份备选约占 2.5 屏。已用「首选满行 + 备选 compact」缓解，但没有折叠或锚点跳转；如果再加内容需要重新评估。
7. **预算页依赖 localStorage**，跨设备不同步、清缓存即丢（ADR-018 / ADR-021 的既定边界）。页面上有醒目警示条。
8. **E2E 脚本在项目外**（工作区根目录 `_e2e-005.mjs`），未纳入 `tests/`，也没有 CI 化。它依赖本机 Chrome 路径与 `next start -p 3100`。
9. **集成测试的 3 项 SKIP** 是「无 token 时显式记 NOT RUN」的占位断言，只在没有凭证的环境执行；有 token 时它们被跳过、真实调用组全部跑。不算失败，但评审看数字时要能区分 26 与 29。
10. **`vitest.config.ts` 有一条 Vite 警告**（ESM 语法被当作 CJS 加载，未来大版本会变成错误）。不影响当前结果，但升级 Vite 前需要把它改成 `.mts` 或加 `"type": "module"`。
